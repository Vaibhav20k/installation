# QA review — 31 October 2026

## Fix status

All four defects below have now been addressed. The original findings are retained as the review record.

- BUG-01: Installation Head read access is independent of approval routing; this does not grant approval or management rights.
- BUG-02: hours confirmation rechecks unresolved punches. Attendance corrections acquire the plan lock before checking confirmed state, so corrections and confirmation are serialized.
- BUG-03: both workforce policies and the Admin form accept at most 900 daily minutes, matching the 09:00-to-midnight planning window. Existing stored settings are not silently rewritten.
- BUG-04: draft date changes preserve the selected team and regenerate daily reservations in the same transaction. Submit and approve also reject an empty team or zero planned hours, covering older affected drafts.
- Five ordinary regression tests now pass in `operations-audit.test.ts`; the known-failure markers were removed. Another 32 related integration tests passed, and TypeScript checking passed.
- Production build passed and the updated local server responds at localhost:3300. The operations browser scenario passed on rerun. Its first run encountered React hydration error 418; it did not reproduce on the next run, and its root cause remains unconfirmed. This warning is not counted as fixed by the four changes above.

The sections below describe the original audit, before these fixes.

## Locations and causes

- BUG-01: `src/server/services/workforce.ts`, around lines 258 and 284. Employee assignment checks do not independently exempt the Installation Head.
- BUG-02: `src/server/services/workforce.ts`, around line 190. Complete checks open punches; Confirm Hours does not repeat that check. `site-presence.ts` permits corrections until hours are confirmed.
- BUG-03: `src/server/services/operations-policy.ts:10` and the policy form accept up to 1440 minutes. Plan reservations start at 09:00 and reject crossing midnight, allowing at most 900 minutes.
- BUG-04: `src/server/services/planning.ts:111` cancels outdated proposed reservations. The operations approval path in `workforce.ts` checks budget but not that a valid team still exists.

## Backend readiness and scope

The app already has server-side services/actions, database migrations, workflow validation and audit logging. It is not frontend-only. Local sign-in uses demo identities. Production identity-provider integration is still outstanding: the current actor resolver rejects production access when demo authentication is disabled.

This review does not claim every manual acceptance case was tested on a physical device or external PostgreSQL deployment. Real-device GPS, production database behaviour and concurrent-user testing remain acceptance work.

Recommended order: fix the two P1 workforce integrity bugs, then Head access and policy validation; rerun the known-failure assertions as ordinary tests; complete real policies/roles and production authentication before release.
